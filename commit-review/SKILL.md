# 提交审查

## 核心规则

> 审查最后一次提交，只检查安全、性能和逻辑问题，忽略代码风格。每个问题必须给出文件、行号和触发条件。

## 执行步骤

### 1. 获取最后一次提交的改动

- 使用 `git show HEAD` / `git log -1` 查看最后一次提交的完整 diff
- 若仓库无法识别（如无 .git），明确告知用户并请求指定审查范围
- 只审查本次提交引入的改动行，不审查无关存量代码

### 2. 只检查三类问题

- **安全**：注入（SQL/命令/路径/HTML）、敏感信息泄露（密钥、token、日志打印密码）、越权访问、不安全的反序列化、路径穿越、弱加密、输入校验缺失
- **性能**：不必要的高复杂度算法、N+1 查询、循环内 I/O、阻塞操作在热路径、资源泄漏（句柄/连接/内存）、重复计算
- **逻辑**：条件判断错误、边界问题（off-by-one、空值、空集合）、错误处理（吞异常、错误返回）、状态更新错误、并发竞态、类型假设

### 3. 忽略风格类问题

不报告：命名、格式化、缩进、注释风格、代码组织、行数、import 顺序、架构品味。

除非风格问题同时导致安全/性能/逻辑问题，才作为那类问题报告。

### 4. 输出格式（每个问题必须含）

```
[类别: 安全/性能/逻辑] [严重度: 高/中/低] <问题一句话>
文件: <文件路径>
行号: <行号或行号范围>
触发条件: <什么输入/什么环境下触发>
影响: <后果>
```

- 严重度定义：
  - 高：可被利用（安全）、可导致崩溃/数据损坏/重大性能故障
  - 中：特定输入下才会出错，或性能在特定场景明显退化
  - 低：潜在风险、模糊隐患、edge case 边缘

### 5. 报告结构

- 按 安全 → 性能 → 逻辑 分节
- 每节列出确认的问题；没有则不写
- 结尾给出总体结论：该提交是否可安全合并，或需修复后合并

## 验收检查

- [ ] 审查对象为最后一次提交的 diff
- [ ] 只涉及安全、性能、逻辑，无风格噪音
- [ ] 每个问题都给了 文件 + 行号 + 触发条件
- [ ] 有明确结论
