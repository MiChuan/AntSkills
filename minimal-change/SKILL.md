# 最小改动

## 核心规则

> 用最小改动实现。不要为未来需求增加抽象，不要处理实际不会发生的错误。先读相邻文件，匹配项目现有风格。

## 执行步骤

### 1. 动手前读相邻文件

- 读同一目录下功能相近的文件、同一模块的既有实现
- 确认项目里已有的工具函数、已有模式，优先复用而不是新造

### 2. 只做必要的事

- 改动范围只覆盖需求本身；不顺手重构、不重排代码、不改无关命名
- 不加未来需求才需要的抽象：不引入接口、泛型、配置项、扩展点、缓存层，除非当前需求确实需要
- 不处理实际不会发生的错误：不为不可能出现的分支写防御代码；除非证据表明该情况会发生

### 3. 匹配现有风格

- 命名：与相邻文件一致（函数/变量/文件命名习惯）
- 结构：沿用项目现有的文件组织方式
- 错误处理：与所在模块一致（同一种异常/返回约定）
- 注释：跟随项目既有注释语言与密度；不为显然的代码加注释

### 4. 若需求与现状冲突

- 如果"最小改动"与"用户要求的某些未来扩展"冲突，以用户当前明确要求为准，但指出哪些部分是为了扩展而额外增加的

## 验收检查

- [ ] 改动只覆盖需求本身，没有顺带重构
- [ ] 没有为不存在的未来需求增加抽象
- [ ] 没有处理实际不会发生的错误
- [ ] 风格（命名、结构、错误处理、注释）与相邻文件一致
- [ ] diff 中每一行改动都有必要
