# 先复现，再修复

## 核心规则

> 先不要修复。写出能稳定复现问题的最小测试，确认 Bug 真实存在后，再根据证据定位根因。

## 执行步骤

### 1. 写最小复现测试（禁止先改业务代码）

- 用项目现有的测试框架与目录约定（先查项目用 pytest / unittest / jest / vitest 等，以及测试放在哪里）
- 最小测试的定义：
  - 只覆盖触发该 Bug 的输入与调用路径
  - 不依赖外部服务可跳过；若必须依赖网络/DB，先写一个本地可控版本的复现
  - 测试断言的就是用户报告的现象本身
- 先跑一遍测试，确认其状态：

| 结果 | 含义 | 下一步 |
|------|------|--------|
| 测试失败且失败原因与用户描述一致 | Bug 真实存在 | 进入步骤 2 |
| 测试通过 | Bug 未复现，可能与版本/环境/输入细节有关 | 补充更多输入变体；修正复现条件后再继续 |
| 测试无法运行（环境问题） | 复现条件不清 | 先解决环境，不进入修复 |

### 2. 根据证据定位根因

- 只依据复现测试与运行时证据（堆栈、日志、数据流）推断根因
- 用二分法缩小范围：隔离可疑函数，构造能区分"假设 A 成立"与"假设 A 不成立"的输入
- 在代码里确认根因链路：从输入 → 处理 → 输出的每一环都有证据

### 3. 修复

- 修复后先跑复现测试，通过后再跑该模块全部测试，最后跑全量测试
- 修复保持最小改动（见 minimal-change 技能），不改动与根因无关的代码

### 4. 收尾

- 复现测试保留为回归测试，注明它对应的 Bug 现象
- 如果复现测试最终被证明测试本身写错了，也要保留修正后的测试作为行为基线

## 验收检查

- [ ] 修复前已写出最小复现测试并能稳定失败
- [ ] 根因有运行时证据支撑，而非猜测
- [ ] 修复后复现测试通过，且全量测试无回归
- [ ] 未顺手修改与根因无关的代码
