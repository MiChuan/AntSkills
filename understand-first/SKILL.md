# 先理解，再动手

## 核心规则

> 先不要修改代码。先阅读相关代码、测试、配置、依赖和相邻功能的实现，弄清楚项目当前的技术栈、代码约定和可以复用的逻辑。然后用自己的话复述需求，列出关键假设和最小改动方案。只有代码库里找不到答案，并且会影响方案选择的问题，才需要问用户。等用户确认后再动手。

## 执行步骤

### 1. 通读上下文（禁止改代码）

- 用 `Read` / `Glob` / `Grep` 找到并阅读：
  - 目标文件本身及依赖它的调用方（相邻功能）
  - 相关测试与测试目录结构
  - 配置文件（依赖清单、构建配置、运行脚本）
  - 上游/相邻实现中可复用的函数、类、工具方法
- 识别项目的技术栈：语言、框架、构建工具、测试框架、lint 规则
- 识别代码约定：命名风格、文件组织、错误处理模式、注释语言、缩进等

### 2. 用自己的话复述需求

- 用一两段话说明你理解的"用户想要什么"以及"完成后应满足什么验收标准"
- 复述中涉及的任何技术判断都必须有代码依据，标注依据来自哪个文件

### 3. 列出关键假设与最小改动方案

- 列出所有影响方案的假设（例如"该接口只被单个调用方使用"）
- 对每个假设标注：能从代码库验证 / 需要用户确认
- 给出最小改动方案：只列出必要的文件与改动点，明确不改动哪些部分
- 明确说明不做的事（不做预先优化、不加未来需求需要的抽象）

### 4. 提问纪律

- **只有同时满足以下两个条件才允许提问**：代码库里找不到答案，且答案直接影响方案选择
- 优先自己从代码中找答案；找过后仍不确定再问
- 提问时把已查过的证据一并给出

### 5. 等确认后动手

- 在得到用户明确确认之前，不创建、不修改任何文件
- 确认后，按已确认的最小改动方案执行

## 验收检查

- [ ] 已读过目标文件 + 调用方 + 相关测试 + 配置 + 依赖
- [ ] 已识别技术栈和代码约定
- [ ] 已用自己的话复述需求（有代码依据）
- [ ] 已列出关键假设（标注验证来源）与最小改动方案
- [ ] 未修改任何代码（除非用户已确认）
